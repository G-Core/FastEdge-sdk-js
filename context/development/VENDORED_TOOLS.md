# Vendored Build Tools (component imports)

`fastedge-build`'s component-imports flow (see `architecture/COMPONENTIZE_PIPELINE.md`,
"Component imports") uses two prebuilt wasm tools committed under `vendor/` and shipped in the
npm package. Both are jco-transpiled (JS + core wasm on `@bytecodealliance/preview2-shim`), so the
build needs no native binary for them on any OS. They are loaded at runtime through
`src/utils/import-vendored.ts`, never bundled into `bin/`, because each finds its `.wasm` next to
its `.js`.

| Directory | What it is | Source | Regenerate |
|---|---|---|---|
| `vendor/splicer/` | ComponentizeJS's splicer, **unchanged** — generates JS glue for a WIT world and patches the engine's `coreabi_*` hooks | `@bytecodealliance/componentize-js` npm package (`lib/`) | `tools/splicer/vendor.sh` |
| `vendor/component-tools/` | **Our** crate (~100 lines): `plug` (wac-graph), `importWorld` + `imports` (wit-component / wit-parser) | `tools/component-tools/` | `tools/component-tools/build.sh` |

Why vendored rather than npm dependencies: `@bytecodealliance/componentize-js` is 42 MB and
pulls in `@bytecodealliance/jco` (native napi modules), weval and its own wizer — that breaks the
platform-neutral build. There is no wasm build of `wac`, and jco-transpile's wasm-tools can't
extract an interface definition from a component.

## Version coupling

| Thing | Pinned in | Must match |
|---|---|---|
| Splicer version (`0.23.0`) | `tools/splicer/vendor.sh` `VERSION` | The engine's `runtime/fastedge/builtins/embedding/` (vendored from the **same** ComponentizeJS tag — `embedding.cpp` header) |
| `embedding.cpp` | `runtime/fastedge/builtins/embedding/` | The StarlingMonkey submodule it compiles against |
| jco used to transpile component-tools (`1.39.0`) | `tools/component-tools/build.sh` | `@bytecodealliance/preview2-shim` in `package.json` (`^0.30.0`). The splicer (transpiled upstream by jco ~1.15) also runs on this shim |
| wac-graph `0.12`, wit-component / wit-parser `0.262` | `tools/component-tools/Cargo.toml` / `Cargo.lock` | Nothing else in the repo |

## When to update

Nothing breaks if these are never touched: every version above is pinned, and they run only at
build time. Update when one of these happens:

**Splicer + `embedding.cpp` (always together):**
- **StarlingMonkey submodule bump** (`PATCHES.md` rebase). `embedding.cpp` uses StarlingMonkey
  internals and may stop compiling; the splicer patches the engine binary and can panic on an
  engine it doesn't expect. Take the ComponentizeJS release that pins the nearest StarlingMonkey
  commit (its `StarlingMonkey` submodule).
- Users need WIT features the splicer doesn't lower/lift yet (e.g. async / WASI 0.3).
- An upstream splicer or `embedding.cpp` fix we need.

Procedure: set `VERSION` in `tools/splicer/vendor.sh` and run it; copy `embedding/embedding.{cpp,h}`
from the same ComponentizeJS tag into `runtime/fastedge/builtins/embedding/` and re-apply the two
FastEdge changes listed in its header (no `console.log` override; `install()` inert without
`SOURCE_NAME`); rebuild the engine (`pnpm run build:monkey:prod`); run the checks below.

**component-tools:**
- A user's component fails to decode or plug (built by a newer toolchain using Component Model
  features these crate versions don't know).
- FastEdge moves to WASI 0.3 — also update `ALLOWED_IMPORT` in `src/componentize/components.ts`.
- A security fix in a dependency (low risk: inputs are the developer's own files at build time).

Procedure: bump versions in `tools/component-tools/Cargo.toml`, `cargo update`, run
`tools/component-tools/build.sh`, run the checks below. Prerequisites:
`rustup target add wasm32-wasip2` and `cargo install cargo-about --locked --features cli`.

**After any update:** `pnpm run test:unit`, `pnpm run test:integration`,
`pnpm run test:cross-platform` (runs a composed app), and build + run `examples/component-imports/`
fixtures under `@gcoredev/fastedge-test`. After a splicer update, also re-check first-call timing
(`COMPONENT_PERFORMANCE.md`): new glue can use built-ins the Wizer-time warm-up doesn't cover.

## Licensing

- `vendor/splicer/LICENSE` — ComponentizeJS's Apache-2.0 WITH LLVM-exception text, copied as
  published (upstream has no NOTICE file). The `Copyright [yyyy] [name of copyright owner]` line is
  the licence's appendix template, not a field to fill in.
- `vendor/component-tools/LICENSE` — our crate, Apache-2.0 (the SDK's `LICENSE`).
- `vendor/component-tools/THIRD_PARTY_LICENSES.txt` — generated by `cargo about` from
  `tools/component-tools/about.{toml,hbs}` (shipped wasm32-wasip2 dependencies only). Needed
  because the wasm statically includes MIT, Unicode-3.0 and Zlib crates, whose notices must
  accompany copies. Most come from `wasm-metadata`'s default features, which `wac-graph` 0.12
  enables and we can't turn off. If a dependency bump adds a licence not in `about.toml`'s
  `accepted` list, `build.sh` fails — review it before adding.
- `package.json` `files` ships `vendor/**/{*.js,*.wasm,LICENSE,THIRD_PARTY_LICENSES.txt}`.

## CI coverage

| Workflow | When | What runs for component imports |
|---|---|---|
| `pr-tests.yaml` | Every PR | Lint + unit tests (`components.test.ts`, splice case in `componentize.test.ts`; tools mocked) |
| `deploy.yaml` → `build-libs.yaml` | Push to release branches touching `src/**`, `runtime/**` or `vendor/**` | `test:integration` on Linux, incl. `component-imports.test.js`: real builds with the real engine + vendored tools against stub components, plus the error cases |
| `deploy.yaml` → `cross-platform-tests.yaml` | Same | `test:cross-platform` on Ubuntu, Windows, macOS, with native modules blocked and paths containing spaces: builds a TypeScript app against `calculator.wasm`, checks the declarations and that `tsc` rejects a mistyped call, then runs the composed app under `@gcoredev/fastedge-test`; also runs an app whose `fetcher.wasm` component makes its own outgoing request to a local server |

`integration-tests/test-files/components/calculator.wasm` is a real component, committed so CI needs no
Rust toolchain; rebuild it with `build.sh` in the `calculator/` crate next to it. It covers two
interfaces from one file and s32, f64, `result` (an `err` becomes a thrown error with `.payload`),
`list<f64>` (`Float64Array` in JS), record, string and a resource (constructor, method, static
taking borrowed handles and returning an owned one). `fetcher.wasm` (crate `fetcher/`, same layout)
makes an outgoing GET through `wasi:http/outgoing-handler@0.2.12` (via the host, as the app's own
`fetch()` does); a failed request reaches the app as a thrown error. The Linux-only tests still use stub components
that trap if called.
